风险及分析

1. 局部 unused 注解。
   include/linux/compiler_attributes.h 将 __maybe_unused 展开为
   __attribute__((__unused__))，不会删除函数体或改变返回值。
   helper 的函数体保持不变，PROVE_LOCKING=y 时仍调用
   lockdep_is_held(&nft_pernet(net)->commit_mutex)。
   kernel/rcu/Kconfig.debug 中 PROVE_RCU 为 def_bool PROVE_LOCKING。
   关闭配置时 RCU_LOCKDEP_WARN 为 do { } while (0)，编译前丢弃条件；
   注解消除 helper 没有调用者的告警。开启配置时原宏仍检查条件。

2. 三处最终调用均已枚举。
   pipapo_maybe_clone() 使用 rcu_dereference_protected()；
   nft_pipapo_commit() 使用 rcu_replace_pointer()，后者展开至前者；
   nft_pipapo_walk() 在 NFT_ITER_UPDATE 无 clone 时读取 live match。
   条件只用于 RCU 锁检查；没有分配、引用计数或其他运行时副作用。
   nf_tables_valid_genid() 获取 commit_mutex，commit/abort 释放它。
   未更改锁范围、分配失败处理或数据面读者。

3. 迁移时保留属性。
   第 14 项删除旧函数位置、插入新位置时均保留 __maybe_unused。
   从第 2 项到最终项，定义始终唯一且带属性；不会在后续移动时重新
   引入告警。移除全局修改后，相关 7 个文件逐提交与基线完全相同。
   本系列没有代码使用被移除的新增 API，原配置可见性保持一致。

4. flush 所有权修复仍在。
   nf_tables_delsetelem() 将 next-gen 掩码交给 NFT_ITER_UPDATE_CLONE。
   nft_pipapo_do_walk() 可以再次枚举已停用元素，但 nft_flush_set()
   在事务分配、flush、ndeact++、data 引用递减之前过滤它。
   第二次 flush 不会再建立同一元素的删除事务，也不会再次移交释放
   所有权。原始删除仍经 commit/remove 及 RCU 后的释放流程完成。
   过滤未放回 walker，nft_mapelem_activate() 的反向恢复仍可访问
   非活动元素，调用 nft_clear() 并恢复引用。

5. verdict-map 校验修复仍在。
   nft_lookup_validate() 提供 next-gen 掩码；回调在读取 verdict 和
   递归 nft_chain_validate() 之前过滤旧的非活动边，不跳过新插入的
   活动元素。该 hunk 与 flush 检查均来自 e79b47a8615d。

6. RCU 释放和核心 CVE 路径。
   本轮未改 clone 的 NEW/MOD 生命周期、OOM abort、GC scan/queue。
   commit 仍先发布 clone，再 call_rcu() 回收旧 match，之后提交 GC
   回收队列；注解和旧版非调试宏不改变这些步骤。
   ab0beafd52b9 的 get 临时指针修复、fb7fb4016300 的只在 flush 时
   克隆，以及最终 47e65eff5069 的坏 clone 隔离均保留。

排除的疑点

- __maybe_unused 不会关闭调试配置的锁检查：属性不修改函数和宏展开。
- 撤掉宏补丁不需要保留其 6 个依赖：它们只服务于条件被解析后的

- 不将 active 过滤恢复到 walker，避免破坏 abort 的反向恢复。
