nft_pipapo_destroy 告警静态分析

问题摘要

nft_set_pipapo.c:nft_pipapo_destroy() 的实际断言为：

    WARN_ON_ONCE(!list_empty(&priv->gc_head));

它检查集合销毁时私有 GC 队列是否为空。静态代码确认了生命周期遗漏：
pipapo_gc_scan() 在发现过期元素之前就分配、挂接 GC 对象；没有过期
普通元素时 dirty 可以保持 false，nft_pipapo_commit() 随后的早退
绕过唯一的 GC 出队和引用释放路径。当前 HEAD 仍有该缺陷。

输入列出的八个 stable 补丁已全部合入。此告警不等于历史 bad clone
问题。另有 clone 为空时未从 live match 销毁元素的独立所有权遗漏。

本次仅进行源码、提交 diff 和公开报告分析。未复现、构造请求、运行
测试、编译或应用补丁。原始操作序列及运行时 dirty、clone、GC count
未知；确认的是静态可达机制，未认定其为原始事故的唯一执行路径。

GC 所有权与提交控制流

net/netfilter/nft_set_pipapo.c:pipapo_gc_scan()：

            gc = nft_trans_gc_alloc(set, 0, GFP_KERNEL);
            if (!gc)
                    return;

            list_add(&gc->list, &priv->gc_head);

net/netfilter/nf_tables_api.c:nft_trans_gc_alloc() 使用 kzalloc()，
因此新对象 count 为 0。分配成功还持有 net/set 引用：

            trans->net = maybe_get_net(net);
            if (!trans->net) {
                    kfree(trans);
                    return NULL;
            }

            refcount_inc(&set->refs);
            trans->set = set;

GC 对象已经挂接，不意味着对象中已有过期元素。扫描只在发现过期
普通元素时设置 dirty。commit 在扫描之后仍可能执行：

            if (!priv->clone)
                    return;

            if (time_after_eq(jiffies, priv->last_gc + nft_set_gc_interval(set)))
                    pipapo_gc_scan(set, priv->clone);

            if (!priv->dirty)
                    return;

其正常尾部为：

            old = rcu_replace_pointer(priv->match, priv->clone,
                                      nft_pipapo_transaction_mutex_held(set));
            priv->clone = NULL;
            priv->dirty = false;

            if (old)
                    call_rcu(&old->rcu, pipapo_reclaim_match);

            pipapo_gc_queue(set);

nft_pipapo_init() 仍会创建初始 clone 并将 dirty 设为 false。
clone 非空不能证明 dirty 为真。后端 commit 被调用也不能证明这一点。
通用 API 的 nft_setelem_insert() 分支为：

            if (flags & NFT_SET_ELEM_CATCHALL)
                    ret = nft_setelem_catchall_insert(net, set, elem, ext);
            else
                    ret = set->ops->insert(net, set, elem, ext);

catchall 管理由通用 API 完成，绕过置 dirty 的后端 insert。成功的
nft_add_set_elem() 仍登记元素事务；nf_tables_commit() 将集合加入
set_update_list，nft_set_commit_update() 仍调用 nft_pipapo_commit()。
这证明现有源码允许上述状态，不表明原始报告执行了这种操作类别。

唯一私有 GC 排空点在 pipapo_gc_queue()：

            list_for_each_entry_safe(gc, next, &priv->gc_head, list) {
                    list_del(&gc->list);
                    nft_trans_gc_queue_sync_done(gc);
            }

nft_trans_gc_queue_sync_done() 对空批次同步执行 nft_trans_gc_destroy()，
非空批次通过 RCU 延迟销毁。对应释放为：

            nft_set_put(trans->set);
            put_net(trans->net);
            kfree(trans);

跳过该链条会泄漏 GC 对象以及 set/net 引用。nft_set_destroy() 最终
只放下基础 set 引用，无法抵消 GC 引用，因此 set/name 分配也被保留。
所有 gc_head 引用只涉及初始化、扫描入队、queue 出队和析构断言，
没有其他清理线程接管。该空批次路径不支持额外推断元素 UAF 或任意写。

串行生命周期时间线

此缺陷不依赖竞争窗口。nf_tables_valid_genid() 持有 commit_mutex，
直到事务 commit/abort 完成。以下是源码状态顺序，不是复现步骤：

- 集合初始化可留下 clone 非空、dirty=false；通用事务登记不保证
  后端匹配表被修改。
- 后端 commit 内扫描先把分配成功的 GC 对象挂接到 gc_head；没有过期
  普通元素时 dirty 不变。
- 同一 commit 因 !dirty 早退，私有队列未交给回收路径。
- 后续集合删除先撤销 RCU 可见链接，异步销毁工作等待 RCU 后销毁集合。
- nft_pipapo_destroy() 发现 gc_head 非空并 WARN；GC 对象和引用未释放。

销毁调用关系为：

    nf_tables_commit()
      -> nf_tables_commit_release()
      -> nf_tables_trans_destroy_work()
      -> nft_commit_release()
      -> nft_set_destroy()
      -> nft_pipapo_destroy()

synchronize_rcu() 不能释放从未提交给 RCU 的 GC 对象。dead set 跳过
后端 commit 是现有销毁策略，它暴露旧状态但不创建 GC 对象。

相关排除项

- 当前已有 NEW/MOD/ERR 坏 clone 隔离。插入错误路径和 abort 本身不
  执行 GC 扫描；不能将 gc_head 检查解释为历史 dirty clone 检查。
- nft_pipapo_abort() 没有 GC 排空，既有残留不会由 abort 自动修复。
- 首个 GC 分配失败不会入队；扩容失败发生在 dirty 已置位之后。
  该已确认路径不依赖 OOM。
- pipapo_gc_queue() 中 catchall 分配失败不跳过后续私有队列遍历。
- pipapo_reclaim_match() 的 RCU 回调释放匹配表，不负责私有 GC 队列。

缺失的主线语义及配套

commit 8b8a2417558c632f249abebde97adf8c46540de2
Author: Florian Westphal <fw@strlen.de>

netfilter: nft_set_pipapo: prepare destroy function for on-demand clone

当前 6.6 缺少 clone 为空时从 live match 销毁元素的逻辑。成功 commit
已将 clone 置 NULL，而当前 destroy 先释放 live match 表存储，仅在
clone 非空时调用 nft_set_pipapo_match_destroy()。表存储释放不等于
调用 nf_tables_set_elem_destroy()；这是独立的元素所有权遗漏。

主线的对应分支是：

    if (priv->clone) {
            nft_set_pipapo_match_destroy(ctx, set, priv->clone);
            pipapo_free_match(priv->clone);
            priv->clone = NULL;
    } else {
            nft_set_pipapo_match_destroy(ctx, set, m);
    }

应补全这一销毁语义；该补丁单独不能解决 gc_head 非空告警。

commit 532aec7e878b527fcee8877350ab5c5341789626
Author: Florian Westphal <fw@strlen.de>

netfilter: nft_set_pipapo: remove dirty flag

该主线改动删除 commit/abort 的 dirty gate、init 预建 clone、dirty
字段及所有读写。它发表于 2024 年，早于 2026 年 GC split 和本次报告，
属于主线已具备、能消除此回移缺口的语义，不是专门针对此次 syzbot
报告发布的修复。

结合当前 GC split，clone 存在时 commit 完成如下所有权顺序：

    scan -> publish match -> queue/reclaim

clone 不存在时在扫描前返回，不新增 GC 对象。建议先适配 8b8a2417558c
的析构逻辑，再适配 532aec7e878b 的完整 dirty 移除。需要保留当前
GC 初始化、gc_head 断言、pipapo_gc_queue() 和 6.6 void * 元素接口；
GC dirty 写入现在位于 pipapo_gc_scan()，init 错误标签也需核对上下文。

不能把 GC 回收前移到 match 发布之前。9df95785d3d8 的目的正是保证
元素不再对新读者可见后才启动 RCU 回收。只删 WARN 或只清空链表不能
释放 GC/set/net 引用。

另一个相关提交为：
    fb7fb4016300ac622c964069e286dc83166a5d52
    netfilter: nf_tables: clone set on flush only
其 6.6 回移已存在：
    e38f054f0af98224003e600545726fbd96379cfb
它限制必须 clone 的遍历类别，处理另一条 nft_map_deactivate WARN，
并未移除当前 dirty gate。
